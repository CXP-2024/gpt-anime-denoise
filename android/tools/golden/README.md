# Golden test fixtures

Reference data for verifying the Android (Kotlin) port of `denoise.py`
**stage by stage**. Everything here was produced on CPU by the real
`denoise.py` code path - not by a re-implementation - so a diff against these
files measures your port, not the fixture generator.

Generated by `android/tools/generate_fixtures.py` (6B tier) and
`android/tools/generate_v3_fixtures.py` (compact tier).

**Two tiers, two sets of references.** `in_*` / `mid_*` / `out_*` belong to the
6B default. `v3_*` belongs to the optional compact model and is *not* comparable
to the 6B files.

## What is in here

Three fixtures, each named by a tag derived from its source image in
`F:\gpt-anime-denoise\outputs\`:

| tag        | source                                             | crop origin | why it is interesting               |
|------------|----------------------------------------------------|-------------|-------------------------------------|
| `01ee25d8` | `img_01ee25d8...-1_denoise.png` (2160x3840)        | (824, 1203) | pale skin + fine hair strands        |
| `061d63a2` | `img_061d63a2...-1_denoise.png` (2336x3504)        | (912, 1075) | large flat areas (shirt, ribbon)     |
| `4dde2cb0` | `img_4dde2cb0...-1_denoise.png` (3840x2160)        | (1664, 564) | dark scene, sharp line work, eyes    |

The crop is deterministic: a 512x512 window, horizontally centred, with its
vertical centre at 38% of the image height.

For each tag:

### `in_<tag>.png` - 512x512 RGB PNG

The pipeline input, saved as 8-bit RGB. The reference numbers were computed by
**re-opening this exact PNG** (`denoise.open_image`), so the app can read the
same bytes out of `assets/` and start from an identical array.

### `mid_<tag>.npy` - float64, shape (512, 512, 3), values in [0, 1]

`denoise.to_arr(sr)` where `sr = denoise.sr_at(model, src, "cpu")`. This is the
output of the **super-resolution stage only**:

```
small = src.resize((round(W*0.6), round(H*0.6)), Image.BOX)   # DOWN = 0.6
big   = upscale(model, small)          # RealESRGAN x4plus anime 6B -> 4x
sr    = big.resize((W, H), Image.LANCZOS)
mid   = np.asarray(sr.convert("RGB"), np.float64) / 255
```

Compare your ONNX Runtime (or NNAPI) super-resolution stage against this file
directly - it is independent of the L0 stage. For `01ee25d8` the generator
asserts that this inline sequence is bit-identical to `dn.sr_at()`.

`.npy` is a plain numpy array: `numpy.load(open(path, "rb"))`. In Kotlin, parse
the v1.0 header (magic `\x93NUMPY`, 2-byte version, 2-byte header length for
v1.0, then a Python-dict literal with `descr`, `fortran_order`, `shape`) and then
read raw little-endian float64. All fixtures are `descr: <f8` and
`fortran_order: False`, i.e. plain C-order float64.

### `out_<tag>.png` - 512x512 RGB PNG

The full default-method result, i.e.

```python
out = denoise.save_png(denoise.to_img(denoise.l0_smooth(mid, 0.001, device="cpu")), path)
```

`lam=0.001` (`denoise.L0`), `kappa=2.0`, `beta_max=1e5` -> 26 iterations.

The generator asserts that re-reading `out_<tag>.png` gives back exactly
`to_img(l0_smooth(mid))`, so this PNG *is* the reference, not a lossy copy of it.

### Resize intermediates

`in_resize.png`, `resize_boxed.png`, `resize_back.png` isolate the two PIL
resizes that bracket the network, built from `in_01ee25d8.png`:

| file | size | what it is |
|---|---|---|
| `in_resize.png` | 512x512 | copy of `in_01ee25d8.png`, the resize pipeline input |
| `resize_boxed.png` | 307x307 | `src.resize((round(512*0.6), round(512*0.6)), Image.BOX)` |
| `resize_back.png` | 512x512 | `resize_boxed.png.resize((512, 512), Image.LANCZOS)` |

All three were re-verified against `denoise.py`'s own calls and match exactly.
Note `round(512 * 0.6) == round(307.2) == 307` - Python rounds half to even, so
Kotlin's `Math.round` (half up) gives the same answer here but **not** for every
input size; keep Python's banker's rounding for arbitrary W/H.

### `v3_mid_<tag>.npy` and `v3_out_<tag>.png` - the optional compact model

`denoise.py` has no method that uses the small network, so **these are not a port
of an existing code path**. They are the same pipeline with
`realesr_animevideov3_x4.onnx` swapped in for the 6B model:

```python
small = src.resize((round(W*0.6), round(H*0.6)), Image.BOX)
big   = onnxruntime("realesr_animevideov3_x4.onnx", small)    # 4x
sr    = big.resize((W, H), Image.LANCZOS)
mid   = np.asarray(sr.convert("RGB"), np.float64) / 255      # v3_mid_<tag>.npy
out   = to_img(l0_smooth(mid, 0.001))                        # v3_out_<tag>.png
```

Inputs are the same `in_<tag>.png` files. Built by
`android/tools/generate_v3_fixtures.py`.

**The v3 tier must be tested against these files, not against `mid_*` / `out_*`.**
Measured: v3 differs from the 6B result by **148-165 levels** on edge pixels and
~3.3-4.1 levels mean (89-91% of all pixels differ), which fails the 6B gate by a
wide margin. That is expected - it is a different network drawing a visibly
softer picture - not a porting bug. Each tier gets its own reference.

Verified: replaying the v3 ONNX through this pipeline reproduces `v3_mid_*` and
`v3_out_*` **exactly** (max abs diff 0), because the whole tier is float32
through ONNX Runtime with no torch rounding step. That makes v3 the tighter of
the two gates - use the same tolerances as below and it should pass with room to
spare; a max of 1 level is realistic if your pre/post-processing is exact.

v3 fixture timing (this box): SR stage 0.87-2.24 s, L0 5.35-9.21 s.
### `timing.json`

Per-fixture CPU timings of each stage plus the min/max/mean of each `mid` array
(a cheap sanity check that your `mid` array is in the right ballpark).

## How to compare

Do not compare the final PNGs first - compare the stages in order:

1. **Input.** Decode `in_<tag>.png` -> `float32[512][512][3]` in [0, 1]
   (`byte / 255`). Must be exactly equal to `numpy.asarray(img)/255`.
2. **Super-resolution.** Run your model on the 0.6x box-downscaled input, resize
   back with LANCZOS, `/255`. Compare against `mid_<tag>.npy`.
3. **L0.** Feed `mid_<tag>.npy` into your L0 implementation (promote to float64 -
   the reference is float64 throughout) and compare against `out_<tag>.png` /
   `l0_ref.py` output.

`android/tools/l0_ref.py` is a torch-free numpy implementation of stage 3 that
is **bit-identical** to `denoise.l0_smooth` on all three fixtures (verified:
array-equal, and the PNGs are byte-for-byte the same). Use it as the oracle.

## Expected tolerances

The reference is float64 on the CPU. Measured on all three fixtures:

### Stage 2 (super-resolution) - float32 model math

| quantity | measured |
|---|---|
| max abs diff of `mid` vs golden | **0.003922 = exactly 1/255** |
| mean abs diff of `mid` vs golden | 3.7e-7 .. 4.3e-7 |

The 1/255 maximum is inherent: the torch reference rounds to uint8 via
`Image.fromarray((y*255+0.5).astype(uint8))` between the model and the resize,
so any accumulator difference at all can flip one pixel across a rounding
boundary. It is *not* accumulated model error - the mean is ~4e-7.

| pass criterion | value |
|---|---|
| max abs diff | <= 0.0040 (1 level) |
| mean abs diff | <= 5e-6 |
| share of samples off by more than 2 levels | 0 % |

Move the tolerance below that only if you reproduce torch bit-for-bit, which
float32 convolution kernels will not do.

### Stage 3 (L0) - float64 FFTs

| implementation | max abs diff | PNG levels |
|---|---|---|
| float64 FFT (numpy, `l0_ref.py`) | 0 (bit-identical) | 0 |
| float32 FFT (simulated on CPU) | 7.3e-4 .. 1.4e-2 | max 3 levels, mean 0.001, <=0.21% of pixels |

L0 is the derivative of a global FFT, so a float32 FFT is *usable* but visibly
noisy on dark gradients (the 1.4e-2 outlier is one pixel in a dark corner of
`4dde2cb0`). Recommendation for the Kotlin port: **do L0 in double**, not float.
A float32 L0 may be accepted with:

| pass criterion | value |
|---|---|
| max abs diff vs `out_<tag>.png` | <= 4 levels |
| mean abs diff | <= 0.05 levels |
| share of pixels differing at all | <= 1 % |

### End-to-end (both stages)

ORT-6B + float64 L0 vs `out_<tag>.png`: max 2-3 levels, mean 0.0006-0.003
levels, <=0.30% of pixels differ at all. So an end-to-end gate of
**max <= 4 levels and <=1% of pixels differing** is realistic; a stricter
"max <= 1 level" gate is only achievable against `mid` + a double-precision L0.
